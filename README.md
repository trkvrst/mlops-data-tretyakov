## 5. Ответы на контрольные вопросы

1. **Какой объект однозначно определяет версию данных в DVC?**
Версию данных однозначно определяет хэш, записанный в `.dvc`-файле (или `dvc.lock`), который, в свою очередь, зафиксирован в конкретном Git-коммите[cite: 3].
2. **Почему одного Git-коммита недостаточно без DVC remote?**
Git хранит только легковесные метаданные DVC. Сами объемные данные находятся в локальном DVC cache, и без загрузки их в DVC remote другой пользователь или сервер не сможет получить физические файлы при восстановлении[cite: 3].
3. **Чем Dataset version отличается от Dataset ID в ClearML?**
Dataset version — это просто человекочитаемый номер (например, 1.0.0), который пользователи могут вводить неоднозначно. Dataset ID — это строгий уникальный идентификатор конкретного состояния данных в базе ClearML[cite: 3].
4. **Почему `finalize()` нельзя считать созданием следующей версии?**
Метод `finalize()` просто делает текущую версию неизменяемой (immutable), предотвращая дальнейшее добавление файлов, но не порождает новый набор данных[cite: 3].
5. **Как доказать, что ClearML version 2.0.0 создана от базы, а не от 1.1.0?**
Это подтверждается lineage (графом зависимостей): при создании версии 2.0.0 в параметре `parent_datasets` указывается Dataset ID версии 1.0.0 (базы), а не 1.1.0[cite: 3].
6. **Что произойдёт, если после `git switch` не выполнить DVC checkout?**
Метаданные Git переключатся на новую ветку, но реальные рабочие файлы в директории `workspace` останутся от старой ветки, что приведет к рассинхронизации данных и кода[cite: 3].
7. **В каком сценарии удобнее DVC, а в каком ClearML Dataset?**
DVC удобнее для тесной привязки данных к коду при разработке (использование веток Git, разрешение конфликтов слияния скриптов и данных одновременно). ClearML Dataset удобнее, когда наборы данных выступают независимыми артефактами, требующими централизованного хранения и удобного поиска через Web UI для различных ML-экспериментов[cite: 3].
